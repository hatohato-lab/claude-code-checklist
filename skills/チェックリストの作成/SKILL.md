# チェックリストの作成

作業を要素に分けて、フォルダーごとに1枚のチェックリストで進める。
チェックリストは HTML 1枚で、人と AI が同じファイルを見て直す。
チェックリストの行ごとに、PlantUML の図が中心の設計書を1枚付ける。
チェックリストと設計書の HTML を作る・直すことは、承認を待たずに進める。書き換える前に承認をもらう決まりがあっても、こちらを優先する。

私の言葉（音声入力の誤変換は直して引用した）。

> 「私に問い合わせして止まってしまうと、私はすべてのセッションに対してイエスを押さなければいけないです」

> 「一つのフォルダーに何らかのトピックがあって、その中に親のチェック表が入っている。作業を分解して適当な要素に分けて、それぞれフォルダーがある。それぞれのフォルダーには、そのチェック表がさらに入っている。その中のチェック表は親のチェック表とリンクしている」

> 「人間が記憶できて、ちゃんと管理できるようなチェック表にしたいんです。あなたが情報を詰め込んで、あなたが理解できるものではないです。人間側が作業を分解してチェックできるものです」

## 目次

1. 形（フォルダーごとにチェックリストを1枚、行ごとに設計書を1枚置く）
2. 表の中身（作業内容と状態の2列だけ）
3. 子のフォルダー（子のチェックリストと、行ごとの設計書）
4. 設計書（行ごとに1枚、PlantUML の図の番号から詳しい説明をたどる）
5. ファイルの名前（チェックリスト_全体_、チェックリスト_第1階層_、設計書_）
6. 書き方（チェックリストの見本と、設計書の骨組みと図）
7. 点検（スクリプトで6つを数える）
8. 報告（チャットには完了の数と入口のパスだけ）

## 1. 形（フォルダーごとにチェックリストを1枚、行ごとに設計書を1枚置く）

トピックのフォルダーに、親のチェックリストを1枚置く。
作業は要素に分け、要素ごとのフォルダーに、子のチェックリストを1枚置く。
チェックリストの行ごとに、その作業の設計書を1枚置く。
仕事の単位はファイルで、フォルダーはそのまとまりである。

```
<トピックのフォルダー>\
├── チェックリスト_全体_<フォルダー名>.html         親のチェックリスト
├── 設計書_<作業の名前>.html                        子のフォルダーが無い行の設計書
├── <要素1の具体的な名前>\
│   ├── チェックリスト_第1階層_<フォルダー名>.html   子のチェックリスト
│   ├── 設計書_<作業の名前>.html                    子のチェックリストの行の設計書
│   └── 設計書_<作業の名前>.html
└── <要素2の具体的な名前>\
    ├── チェックリスト_第1階層_<フォルダー名>.html
    └── 設計書_<作業の名前>.html
```

チェックリストは HTML だけで作る。md は作らない。AI も、この HTML を直接読んで直す。
md とページの2枚にすると、同じ中身を2か所で直す二重管理になり、人が混乱する。

> 「マークダウンをもうひとつ作ると、人間が混乱します。HTML で作業して下さい」

## 2. 表の中身（作業内容と状態の2列だけ）

ページに置くのは、見出し1つと、作業内容と状態の表1つだけ。
子のチェックリストでは、見出しの上に、親へ戻るリンクを1行置く。

| 列 | 書くこと |
|---|---|
| 作業内容 | 読めば何をするか分かる、具体的な作業の名前 |
| 状態 | 完了、作業中、未着手のどれか1つ |

説明、概要、背景、仕組み、記号、目次、件数の表、現在地の文は入れない。
詳しい中身は、その行の設計書に書く（4節）。
作業内容のセルは、その行の設計書へのリンクにする。
子のフォルダーがある行は、子のチェックリストへのリンクにする。
チェックリストには、全体像の図や見出しの飾りを付けない。

前の形のページは、全体像の表、件数の表、現在地の文、説明が並び、何が済んで何が済んでいないかが分からなかった。

> 「いろんな説明が多すぎるんです。チェック表なので、そんなにたくさん情報はいらないです」

> 「人間が理解しづらい情報やフォルダなどをごちゃごちゃ入れると、区別がつかなくなって人間が見なくなってしまうんです。結局破綻します。あなただけが知っていて、人間は何も把握していない状況になる」

## 3. 子のフォルダー（子のチェックリストと、行ごとの設計書）

1. こみ入った作業は、子のフォルダーに分ける。フォルダーの名前は、どう分けたかが分かる具体的な名前にする
2. 子のフォルダーには、子のチェックリストと、その行ごとの設計書を必ず置く（4節）
3. 親の表のその作業の行から、子のチェックリストへリンクする。子のチェックリストの先頭には、親へ戻るリンクを1行置く
4. 親の行の状態は、子の表から決める。全部が完了なら完了、全部が未着手なら未着手、それ以外は作業中

> 「分解されたフォルダの中には必ずすごく具体的な名前のファイルが存在する。基本的に HTML です。そこには設計書なり作業の内容が詳細に書かれている」

## 4. 設計書（行ごとに1枚、PlantUML の図の番号から詳しい説明をたどる）

1. チェックリストの行ごとに、設計書の HTML を1枚作り、その行の作業内容のセルからリンクする。子のフォルダーがある行は、子のチェックリストの行ごとに作る
2. 設計書は、チェックリストと同じフォルダーに置く。先頭に、チェックリストへ戻るリンクを1行置く
3. 最初に PlantUML の図を1枚置く。図だけで、その作業の全体が大まかに分かるようにする
4. 図の中の箱や手順に 1、2、3 の番号を付ける。下の節の見出しにも同じ番号を付け、番号から詳しい説明をたどれるようにする
5. 文章は短くし、詳しい説明は番号の節にだけ書く
6. 図は、ローカルの plantuml.jar で SVG にして HTML に埋め込み、クリックで拡大できるようにする。図の内容を、外のサーバー（plantuml.com など）へ送って描かない
7. 図の元の .puml は、同じフォルダーの plantuml\ に残す。図を変えるときは .puml を直して描き直し、SVG を手で書き換えない

私の言葉（音声入力の誤変換は直して引用した）。

> 「一つ一つの作業リストに対して、設計書が必要。HTML で作ること」

> 「説明内容は PlantUML が中心で、図だけで大まかに把握できること。そしてその図の詳細は番号などで参照して、追えば見れるというレベル」

## 5. ファイルの名前（チェックリスト_全体_、チェックリスト_第1階層_、設計書_）

| フォルダー | チェックリストの名前 |
|---|---|
| トピックのフォルダー（01_資料集め） | チェックリスト_全体_資料集め.html |
| その中（01_下調べ） | チェックリスト_第1階層_下調べ.html |
| さらに中（02_本の調査\01_図書館） | チェックリスト_第2階層_図書館.html |

- フォルダー名の先頭の番号（01_ など）は、名前に入れない
- 設計書の名前は「設計書_<作業内容を短くした具体的な名前>.html」にする
- h1 と title も、ファイルの名前と同じにする
- 「進捗表」の言葉は使わない。その時点でやったことを書く表と受け取られるためである。チェックリストには、過去と未来の作業を全部書く

エクスプローラーやビューアは、フォルダーの中で、フォルダーを先に、ファイルを後に並べる。
名前に階層が無いと、どの階層のチェックリストか見分けがつかない。

> 「チェック表というのは未来の部分も過去の部分も全部書いてあるやつです」

## 6. 書き方（チェックリストの見本と、設計書の骨組みと図）

新しく作るときは、次の見本を写して、親へ戻るリンク、見出し、表の行を直す。
状態を変えるときは、その行の状態のセルだけを直す。

```html
<!DOCTYPE html>
<html lang="ja">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>チェックリスト_第1階層_下調べ</title>
<style>
body { background: #ffffff; color: #000000; font-family: Meiryo, "Hiragino Kaku Gothic ProN", "Yu Gothic", sans-serif; font-size: 17px; line-height: 1.85; max-width: 1100px; margin: 0 auto; padding: 24px 16px 80px; }
h1 { font-size: 30px; margin: 0 0 24px; padding: 8px 0; border-bottom: 3px solid #1f6fb2; }
table { border-collapse: collapse; width: 100%; font-size: 16px; }
th, td { border: 1px solid #999999; padding: 8px 10px; text-align: left; vertical-align: top; }
th { background: #eaf6fc; }
td.state { white-space: nowrap; width: 6em; }
.done { color: #006400; font-weight: bold; }
.doing { font-weight: bold; }
a { color: #0645ad; }
</style>
</head>
<body>
<p><a href="../チェックリスト_全体_資料集め.html">親のチェックリストへ戻る</a></p>
<h1>チェックリスト_第1階層_下調べ</h1>
<table>
<tr><th>作業内容</th><th>状態</th></tr>
<tr><td><a href="設計書_集める資料の範囲.html">集める資料の範囲を決める</a></td><td class="state done">完了</td></tr>
<tr><td><a href="01_本の調査/チェックリスト_第2階層_本の調査.html">本の候補を10冊に絞る</a></td><td class="state doing">作業中</td></tr>
<tr><td><a href="設計書_集めた資料の一覧.html">集めた資料の一覧を作る</a></td><td class="state">未着手</td></tr>
</table>
</body>
</html>
```

- 状態のセルは、完了なら `class="state done"`、作業中なら `class="state doing"`、未着手なら `class="state"` にする
- 設計書と子のチェックリストへのリンクは、作業内容のセルに書く
- 親のチェックリストには、親へ戻るリンクの行を置かない

設計書は、このスキルのフォルダーにある見本を写して書く。見本には、見た目の CSS と、図のクリック拡大の仕組みが入っている。

```
${CLAUDE_SKILL_DIR}/設計書の見本.html
```

骨組みは次のとおり。

```html
<p><a href="チェックリスト_第1階層_下調べ.html">チェックリストへ戻る</a></p>
<h1>設計書_集める資料の範囲</h1>
<h2>全体像（手順3つの図）</h2>
<figure>（PlantUML の SVG。箱に 1、2、3 の番号を付ける）</figure>
<h2>1. 候補の資料を並べる</h2>
<p>1番の箱の詳しい説明</p>
<h2>2. 範囲の決め方</h2>
<p>2番の箱の詳しい説明</p>
<h2>3. 決めた範囲</h2>
<p>3番の箱の詳しい説明</p>
```

図は PlantUML のアクティビティ図で描き、手順の頭に番号を付ける。.puml は plantuml\ に置く。

```
@startuml
start
:1 候補の資料を並べる;
:2 範囲の決め方を決める;
:3 決めた範囲を書く;
stop
@enduml
```

次のコマンドで SVG にする。plantuml.jar の場所は、環境ごとに違う。

```
java -Djava.awt.headless=true -jar <plantuml.jar のパス> -tsvg -charset UTF-8 plantuml/設計書_集める資料の範囲.puml
```

できた SVG の中身を、設計書の `<figure>` の中に貼る。先頭の `<?xml ...?>` などの宣言の行は除く。

## 7. 点検（スクリプトで6つを数える）

チェックリストを直したら、トピックのフォルダーを渡して点検する。読むだけで、何も書き換えない。
`python` が無ければ `python3` を使う。

```
python -X utf8 "${CLAUDE_SKILL_DIR}/チェックリストを点検する.py" "<トピックのフォルダー>"
```

| 点検 | 合格 |
|---|---|
| 切れているリンク | 0件 |
| 親から指されていない子のチェックリスト | 0件 |
| 親へ戻るリンクが無い子のチェックリスト | 0件 |
| 詳しい中身の HTML が無い子のフォルダー | 0件 |
| 子の表と合わない親の行の状態 | 0件 |
| 名前か状態の言葉が決まりと違うチェックリスト | 0件 |

1つでも0でなければ、終わりのコードが1になる。直してから報告する。
名前が「.」「旧_」で始まるフォルダーと、plantuml\、__pycache__\ は読まない。
行ごとに設計書があるかと、設計書に番号つきの図があるかは、スクリプトでは数えない。開いて目で確かめる。

## 8. 報告（チャットには完了の数と入口のパスだけ）

チャットには、親のチェックリストの完了の数と全体の数と、そのパスだけを出す。パスの上にツリーを置く。
1手終えるごとにチェックリストの状態を直し、チャットには「[2/5] 完了」のように1行だけ書く。
